# 会议引用锚点闭包初审

- 审查日期：2026-08-24
- 审查范围：`content/meetings` 当前 9 篇公开 JSON、内容 Schema 与自动门禁
- 审查边界：只检查公开 JSON 的结构化时码，没有读取私有逐字稿，没有修改会议 JSON，也没有记录私有路径、资源标识或发言原文

## 结论

原门禁分别校验 `coreTopics[].anchor`、`discussion[].anchors[]` 与 `sourceAnchors[].time` 的格式和时长边界，却没有检查“内容引用是否已进入来源证据清单”。因此，只要三处时码各自格式正确，即使主题或讨论引用无法从 `sourceAnchors` 找到对应记录，页面仍会通过。

本次新增单向闭包规则：每个非空主题/讨论引用时码必须至少匹配一条 `sourceAnchors[].time`。来源清单可以包含额外证据，同一来源时码也可以被多处重复引用。缺口使用稳定错误码 `ANCHOR_NOT_DOCUMENTED`，只报告公开文件名和 JSON 字段路径，不携带引用值。

新规则下，当前 9 篇中 5 篇通过、4 篇失败，共发现 41 个缺口，且全部错误均为 `ANCHOR_NOT_DOCUMENTED`。这是预期的迁移门禁结果；内容负责人需要回到已授权来源核对后补写去敏的 `sourceAnchors` 记录，不能机械复制时码或虚构证据说明。

## TDD 与回归证据

先加入合成回归测试，旧实现出现 2 个预期失败：未生成 `ANCHOR_NOT_DOCUMENTED`，无法定位主题与讨论中的闭包缺口；重复引用/额外来源证据和经审计的无转写 `insufficient` 样例仍通过。

最小实现后，测试覆盖以下行为：

- 分别定位 `coreTopics[].anchor` 与 `discussion[].anchors[]` 的缺口；
- `sourceAnchors` 允许额外证据，一条记录可以覆盖同一时码的重复引用；
- 经审计的无转写 `insufficient` 页面在 `coreTopics`、`discussion`、`sourceAnchors` 三个数组全空时继续通过；
- 人读和 JSON 报告均不回显未记录引用值。

本次验证结果：

- `npm run test:coverage`：内容门禁 53/53、站点 28/28 测试通过；内容门禁行/分支/函数覆盖率为 97.09% / 87.63% / 100%，站点为 98.16% / 90.32% / 100%；
- `npm run check`：0 errors、0 warnings、0 hints；
- 当前 9 篇执行 `content:check`：按预期以退出码 1 阻断，5 篇通过、4 篇失败，41 个问题全部为 `ANCHOR_NOT_DOCUMENTED`；机器报告的这些错误没有 `details`，也没有回显任何时码值。

## 规则边界

自动门禁能证明引用时码与来源清单形成结构闭包，不能证明时码确实支持页面中的主题、推理或结论。补齐记录时仍需人工核对已授权来源，并让 `sourceAnchors[].note` 只描述去敏主题，不复制隐私发言。
