## 自动门禁缺陷与修复

### 规范化与资源标识

- 扫描前执行 Unicode NFKC、移除常见零宽字符，并最多两次安全 URL 解码。
- 阻断 `minute(s)_token`、`note_id` 的点号、连字符、空格、camelCase、全角和零宽变体。
- 阻断常见飞书文档、妙记、Wiki、Base、Drive 等裸 token 前缀。
- 阻断带协议、protocol-relative、无协议、URL 编码及根域私有路径；保留公开开发文档和产品首页白名单。

### 联系方式、账号与秘密

- 手机号覆盖中国大陆常见格式与带明确电话语境的国际号码；邮箱和 IPv4 支持全角变体，新增 IPv6。
- 新增显式账号、微信号、`open_id`、`user_id`、`union_id` 等语境和字段名检测。
- 新增 Bearer、JWT、GitHub/GitLab、AWS、Slack token 与 PEM 私钥检测；密码/验证码支持多余标点和全角数字。

### 语义敏感信息

- 对带门牌的详细地址、高置信具名客户/供应商、个人薪资/存款/负债，以及客户合同金额和供应商底价进行阻断。
- 泛化后的“客户角色”“供应商管理”“财务口径”“目标地区”等治理措辞不会因关键词单独出现而误报。
- 规则故意只覆盖高置信语境；不能可靠机械判断的身份拼图继续由人工审查。

### 文件名与报告泄漏

- 敏感文件名、不可读目录、坏 JSON、未知字段名、标题、`id` 和报告元数据使用统一遮罩，不回显原值。
- CLI 未知参数不再回显参数内容；JSON 报告写入失败不再打印底层文件系统错误或输出路径。
- 机器可读 JSON 与人读报告均有回归测试，保证遮罩后的值不会反向泄漏。

## 全仓可发布文件核对

- Git 跟踪文件仅包括项目规则、README、schema、审查文档、4 篇会议 JSON、质量工具、测试与合成 fixture。
- `.gitignore` 已覆盖 `.env*`、`private/`、`raw/`、构建和测试输出；仓库未发现这些内容被跟踪。
- 全仓高置信模式扫描仅命中规则说明和审查文档中的禁用字段名称，没有命中实际 token、URL、联系方式或秘密值。
- 测试中的地址、主体、账号和秘密均是明确的合成 fixture，不来自真实会议。

## 仍需人工处理的风险

1. **公开来源标题与活动品牌**：源标题是知识溯源的一部分，也可能成为外部搜索入口。是否保留必须由内容负责人基于活动公开性、参会者预期和授权判断，工具不能代替授权。
2. **间接身份拼图**：日期、时长、细分业务、事故类型、创业路径和活动品牌单独看不敏感，组合后可能让熟人识别。门禁不能证明匿名性。
3. **客户和供应商语义**：规则能抓显式名称和金额，无法识别昵称、行业唯一描述、上下游关系网或被改写的商业秘密。
4. **地点**：规则能抓带省市区和门牌的高置信地址，不能穷举地标、路线、酒店、园区别称或多个模糊地点的组合。
5. **财务**：规则能抓显式个人/客户/供应商金额，无法判断不带语境的数字、比例或经营指标是否可反推出主体。
6. **历史提交与外部生成物**：本审查覆盖当前 Git 跟踪内容，不证明远端 Git 历史、Actions artifact、搜索缓存或已发布页面从未包含敏感信息。

## 发布建议

1. 每批内容除 `npm run content:check` 外，至少安排一名未参与整理的人做身份拼图审阅。
2. 对含公开活动品牌、独特项目事故或细分供应链组合的页面，发布负责人应记录“保留依据 / 授权 / 可接受风险”。
3. 任何从私有映射台账生成的文件或报告必须留在仓库外；不要把失败报告直接粘贴到公开 issue。
4. 若发现疑似泄漏，先停止构建与发布，再检查 Git 历史、Pages 构建物和缓存，不要只修改当前文件。
